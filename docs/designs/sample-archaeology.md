## Problem Statement

SpotOn today researches one song and renders a report. Its charts come from Spotify audio-features, an endpoint Spotify closed to new apps in late 2024, so the code falls back to LLM-estimated numbers (`api/research-song.ts:165`, `api/_lib/researchAgent.ts:157`, `source: 'estimated'`). The result reads once and is forgotten, and the numbers are guesses.

The new feature: paste a song, dig through what it samples, what that samples, and so on, and **prove each link from the audio**: where the sampled material sits, how far it was pitched, how much it was sped up, and play both clips lined up.

## What Makes This Cool

- "Stronger" → Daft Punk → a 1979 Edwin Birdsong record, three clicks, and you hear the same riff age 30 years.
- Each edge shows "found at 0:07 · +1 semitone · 1.06× faster" and an aligned A/B play button.
- Turntable vs. time-stretch: when pitch shift ≈ 12·log2(speed ratio), the sample was sped up like vinyl (the classic "chipmunk soul" move). When they diverge, it was time-stretched in software. The app can say which, from measurement.
- Every link comes from Genius data; every measurement comes from audio. Nothing is invented by the LLM.

## Constraints

- Budget: free local development, short-lived cloud. No paid resource without the owner's approval; verify pricing before proposing one. Teardown documented.
- Public repo: no audio files, keys or personal data committed. Preview audio is fetched at runtime and never stored in git.
- Audio source: iTunes 30-second previews only (already used by `useAudioPreview`). Spotify no longer returns `preview_url`.
- Genius API: on-demand lookups with caching and polite rate limits, no bulk crawl (API terms likely forbid mass harvesting; confirm before any batch job).
- No invented metrics. Every number in the README or resume comes from the eval harness.

## Premises (agreed)

1. Audio matching is the main event; the family tree is the frame around it.
2. Genius links decide WHICH pairs to check; audio decides WHERE and HOW (offset, pitch, speed). The system never invents a link Genius doesn't list.
3. Only 30-second previews are used, so "not in this clip" is an expected, honest answer.
4. Success is measured on a labeled eval set, and that number is the resume bullet.

## Landscape (generic-term search, 2026-11-01)

- Plain landmark fingerprinting (Shazam-style) breaks under pitch/tempo change. Open-source tools that handle both: Panako (Java, ISMIR 2014, reports offset + pitch/time modification) and qfp (Python, Sonnleitner & Widmer quad hashing).
- Automatic sample identification is active research: Sony AI's multi-track contrastive model (arXiv 2510.11507, code at github.com/sony/sampleid) and a CNN trained on artificial data (Cheston, Van Balen, Durand 2025: +13% over landmark fingerprinting, locates the sample within 5 s for half the test tracks).
- Both papers name the lack of large annotated datasets as the bottleneck. Patent literature notes small shifts (1-5%) are the most common.
- **Insight:** research does retrieval (find an unknown source in a huge index). SpotOn does verification and localization of a known pair, because Genius names the candidate. That turns a hard search into a 1:1 alignment that runs on a laptop. Genius pairs also form a (noisy) labeled set, the thing the papers say is missing.

## Approaches Considered

- **A: Browser-only matcher** (Web Audio chroma in JS). Rejected: weak ops story, DSP harder to test in JS, and cross-origin reads of iTunes audio unverified.
- **C: B plus baseline comparison** against qfp / Panako. Deferred, not rejected: the eval harness is built so a baseline is one more matcher behind the same interface.

## Recommended Approach: B, Python matcher service + eval harness

### Architecture

```
Browser ──► SpotOn app (existing Node/Edge)  /api/sample-tree?genius_id=…
              │  BFS over Genius song_relationships (samples, interpolates), depth ≤ 3, fan-out cap
              │  resolve each song to an iTunes preview URL (reuse the useAudioPreview lookup logic)
              │  cache tree + each pair result in Redis (key includes matcher version)
              ▼
            matcher (new, Python, Cloud Run, private)   POST /match {child_url, parent_url}
              - URL allowlist: Apple preview hosts only (SSRF guard)
              - decode AAC (ffmpeg in image) → mono 22.05 kHz
              - CQT chroma, hop 512
              - search semitones −6..+6 and speed ratio 0.80..1.25, small shifts first
              - normalized cross-correlation over time offsets
              - confidence = peak vs. background distribution (other offsets / unrelated clips)
              → {found, child_offset_s, parent_offset_s, semitones, speed_ratio, mode: turntable|stretched, score, confidence, version}
```

- Matcher is not public: Cloud Run IAM invoker restricted to the app's runtime service account (ID-token auth). Locally it runs as a third container in `compose.yaml`.
- Matcher calls draw from a budget like `takeResearchBudget` (`api/_lib/rateLimit.ts`) so the public demo can't be used to burn CPU.
- `interpolates` edges (re-played, not sampled) are checked with the same chroma method but labeled separately; a match there means "same melody", not "same recording".

### UI (text wireframe)

```
Stronger — Kanye West
└─ samples ─ Harder Better Faster Stronger — Daft Punk
│            ✓ found at 0:07 in Stronger ↔ 0:41 in HBFS · +0 st · 1.00× · conf 0.91   [▶ A/B]
│            └─ samples ─ Cola Bottle Baby — Edwin Birdsong
│                         ✓ found · +1 st · 1.06× · turntable                         [▶ A/B]
└─ samples ─ (other)      — not in these previews (both clips checked)
```

A/B playback uses the existing audio element: play the parent from its offset at `playbackRate = speed_ratio` with pitch preservation off for turntable matches, so it lines up with the child by ear.

### Evaluation (the proof)

- **Synthetic set (CI, offline, deterministic):** generate clips in code (synthesized chord loops plus noise and a drum-like layer), apply known pitch/speed/offset transforms, mix under other material. Exact ground truth, no copyrighted audio in the repo.
- **Real set (manual run, not in CI):** ~50 `samples` pairs from Genius, fetched at eval time, never committed. Report detection rate, plus offset/semitone accuracy on ~15 pairs hand-labeled by ear.
- **Negatives:** ~50 unrelated pairs to measure the false-positive rate. Without this, the detection rate is meaningless.
- Report the numbers as measured, including "not in preview" cases. Thresholds for CI are set after the first measurement, not before.

### Ops (reuses the existing track)

Second Cloud Run service in Terraform (min 0, IAM-only invoker), same CI pattern as `container.yml` (SHA-pinned actions, digest-pinned base, Trivy, smoke test), log-based latency metric + alert. Cold start with librosa/numba and memory need (likely 1 GiB) must be measured; re-check Cloud Run free-tier pricing for the new size before deploying.

## Spike Result (2026-11-01): no-go as written, go with a changed detector

Scratch code, not in the repo: iTunes previews for 11 songs, 6 known pairs, 24 unrelated pairs as controls. Feature × score variants tried: chroma raw, chroma z, CQT raw, CQT z (z = window peak vs. the pair's own offsets).

| Variant | Real pairs above every unrelated pair |
|---|---|
| chroma, raw score | 0 / 6 (unrelated max 0.81 vs. best real 0.56) |
| chroma, z score | 0 / 6 |
| CQT, raw score | 0 / 6 |
| CQT, z score | 1 / 6 (Stronger ← HBFS, z 7.36 vs. unrelated max 7.25; barely) |

Known-answer test (CQT z): a 10 s transformed excerpt planted at a known spot under another song.
- Pitch, speed and alignment recovered in 4 / 5 cases, judged on the same diagonal: child and parent offsets shifted together along the planted region. The automatic OK check was too strict and flagged 2 of these as misses.
- The slowed-down case (0.84×) failed.
- Confidence of the correct recoveries: z 2.7 to 13.1. Unrelated real pairs: median 4.0, max 7.3. So the matcher can **locate** a sample it is told is there, but its score cannot **decide** whether one is there.

What this means for the design:
1. Whole-spectrum sliding correlation is a usable *estimator* (offset / pitch / speed) but not a *detector*. Chroma-like features match any two songs sharing chords in a key.
2. The found/not-found decision needs a discriminative method: pitch- and tempo-robust landmark fingerprinting (Panako or qfp style), or the Sony `sampleid` embedding model. Approach C's "baseline" becomes the core detector; the CQT matcher stays as the refinement step.
3. Estimates bunch at the grid edges (0.80 and 1.23 to 1.25), which suggests the score has a bias that favours long or short stretched clips. Fix before trusting speed estimates.
4. Unknown and still open: how often the sampled section lies inside both previews. The A/B renders from the spike need a human listen to tell "matcher wrong" from "sample not in clip".

## Spike 2 and Build (2026-11-01)

**Detector.** Triplet fingerprints in the style of Panako: CQT peaks (3 bins per semitone) grouped into an anchor plus two of the loudest later peaks. The hash keeps frequency differences and the ratio of the time gaps, so it does not change under pitch or speed shifts. Hits vote on (pitch shift, speed, offset). On the spike set:
- First version (nearest-peak pairing, exact hashes): 1/6 real pairs above the unrelated pairs. Synthetic plants recovered 2/6.
- Loudest-in-zone pairing, coarser hash: synthetic 5/6 with exact pitch and speed. Real pairs were still swamped by one "hub" song (Gold Digger's sparse drums matched everything).
- Normalizing the score against unrelated background songs ("s-norm", as in speaker verification): Ice Ice Baby ← Under Pressure 19.8 against an unrelated maximum of 6.1. Normalizing a pair against its own other clusters instead did worse.

**Decision changes vs. the approved design:**
1. Detector = fingerprint votes plus background normalization. The chroma/CQT correlation from spike 1 is dropped (it could locate but not detect).
2. No family tree in Postgres: the tree is read from Genius on demand and cached a day.
3. iTunes search is rate-limited (~20 calls/min per IP, hit during the eval). The browser resolves previews (it already did for the player), and the matcher's 22 background songs use one batched `/lookup` by track id.
4. PyAV instead of apt ffmpeg: the image has no apt packages beyond the base image, and Trivy finds no fixable HIGH/CRITICAL.
5. Cloud Run deployment is deferred. The matcher has no auth yet, so it runs only on a private network (compose). On Vercel the tree shows without audio buttons (`X-Audio-Check: off`).

**Results** (matcher/eval/RESULTS.md, threshold 7.5 fixed before the test split ran):
- Held-out test split: 4/30 real pairs confirmed, 0/60 unrelated pairs.
- Dev split: 0/6. In spike 2 the Ice Ice Baby pair scored high with the Hot Space "Under Pressure". The eval's iTunes match picked a 2017 single-version release whose preview covers a different part. Preview choice moves results as much as the detector does.

**Next:** try several releases per song to cover more of each recording; add Cloud Run IAM auth to the matcher and deploy it behind the demo scripts; trim the image (librosa pulls numba, LLVM and scikit-learn for one CQT call).
