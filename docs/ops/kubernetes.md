# SpotOn on local Kubernetes (kind)

Local only: a single-node [kind](https://kind.sigs.k8s.io) cluster inside the Colima VM. This is not managed/cloud Kubernetes.

```
scripts/kind-up.sh                                   # cluster, image build + kind load, config/secret from .env, apply, wait
kubectl -n spoton port-forward svc/spoton 8080:80    # http://127.0.0.1:8080
kind delete cluster --name spoton                    # teardown
```

| Object | What and why |
|---|---|
| `Deployment/spoton` | 2 replicas; rolling update `maxUnavailable: 0, maxSurge: 1`; startup/readiness/liveness on `/healthz` (never touches Redis); requests 100m/96Mi, limits 500m/256Mi; non-root, read-only rootfs, no privilege escalation, all capabilities dropped; `preStop: sleep 5` |
| `Service/spoton` | ClusterIP 80 → named port `http` |
| `ConfigMap/spoton-config` | Non-secret settings; generated by the script (cache URL points at the in-cluster Redis) |
| `Secret/spoton-secrets` | API keys straight from `.env`; never committed, never printed |
| `Deployment/redis`, `Deployment/redis-http` | Ephemeral cache plus serverless-redis-http so the unchanged Upstash client works |

## Findings (measured 2026-11-01; kind v0.33.0, kubectl v1.37.2, Colima 2 vCPU / 4 GB)

**1. serverless-redis-http OOMKilled on first deploy (unplanned).** Exit 137 in a crash loop at a 256Mi limit, though the same image idles at 52 MiB (startup peak 65 MiB) in Docker. Ruled out: the memory limit alone, the CPU limit (0.25 CPU in Docker ran fine), and service-link env vars. Cause: open-files limit. `ulimit -n` is 1024 in Docker but 1,073,741,816 in a kind pod, and the BEAM sizes its port table from it (in Docker, raising nofile to 1,048,576 already lifts the peak from 65 to 81 MiB). Fix: `ERL_MAX_PORTS=65536`. Result: Running, 0 restarts, peak 68 MiB under 256Mi.

**2. `kubectl port-forward` is not load-balanced.** Killing a pod during a port-forward to the Service failed 65 of 75 requests, because port-forward pins one pod. The same drill from an in-cluster client through Service DNS: 99/100.

**3. One request lost on pod termination; fixed with preStop.** That 1/100 was a connection refused: SIGTERM and endpoint removal race, and the server stopped accepting first. With `preStop: sleep 5`, two runs of the drill gave 100/100 and 100/100.

**4. Bad image rollout is contained.** `spoton:does-not-exist` → new pod `ImagePullBackOff`, both old pods stayed Ready (2/2), EndpointSlice showed `true true false`. `kubectl rollout undo` restored it; it also warns that undo bypasses the applied manifest, so the file stays the source of truth.

**5. Memory limit drill.** At 48Mi the app ran fine (peak 22 MiB, current 18 MiB), so the 96Mi request is oversized; Stage 7 load tests decide the right value. At 16Mi: `OOMKilled` (exit 137), `CrashLoopBackOff` after 3 restarts, startup probe failures in events, old pods still 2/2. `kubectl apply -f k8s/app.yaml` restored it.

End to end through the cluster: fresh report 5.7 s (Gemini + tools), repeat < 0.1 s from the in-cluster Redis.

## Debugging commands used

```
kubectl -n spoton get pods -o wide
kubectl -n spoton describe pod <pod>          # events: pulls, probes, OOM, back-off
kubectl -n spoton get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'
kubectl -n spoton logs <pod> --previous       # logs of the crashed container
kubectl -n spoton exec <pod> -- cat /sys/fs/cgroup/memory.peak
kubectl -n spoton get endpointslices -l kubernetes.io/service-name=spoton
kubectl -n spoton rollout status|undo deployment/spoton
```
